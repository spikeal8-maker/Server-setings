# Перенос школьной ASA Lab: приложение, журналы и GPU

Связанная программа: [asa-lab#909](https://github.com/spikeal8-maker/asa-lab/issues/909).
Это последовательность настройки и шаблоны, а не готовый образ машины.
Проверка на новой физической машине и приёмка100 учеников остаются NOT_RUN.
Кандидат приложения находится в [PR926](https://github.com/spikeal8-maker/asa-lab/pull/926),
HTTP-проверки — в [PR30](https://github.com/spikeal8-maker/Server-setings/pull/30),
приватный QA fixture — в [PR31](https://github.com/spikeal8-maker/Server-setings/pull/31).
Нельзя выдавать незавершённый PR или отдельный успешный health за принятый выпуск.

## Что переносится

| Источник | Содержимое |
|---|---|
| GitHub asa-lab | Приложение, Scratch, миграции, Compose, менеджер установки, сборщик журналов |
| GitHub Server-setings | Настройка Ubuntu/1Panel, школьный ingress, тесты и этот порядок переноса |
| Закрытый проверенный backup ASA | PostgreSQL, объекты MinIO, прежние ключи и конфигурация приложения |
| Отдельное хранилище GPU | Модели Ollama/ComfyUI, custom nodes и рабочие workflow |
| Приватная настройка нового узла | Tailnet, ключ машинного SSH, проверенный host key, адреса и HTTPS origin |

Git не содержит пользователей, дампы, модели, cookie или приватные ключи.
Новая генерация ключей шифрования ASA вместо переноса прежних ключей не является восстановлением.
Приватный офлайн-ключ age не устанавливается как постоянный ключ сервера.

## Приложение и данные

1. На действительно новой Ubuntu выполните базовую настройку по [начальному маршруту](00-НАЧНИ-ЗДЕСЬ.md).
   На существующем сервере сохраняйте каталог, Compose project, профиль и тома.
   Школьный `asa-lab-school` и исторический тестовый `asa-lab-dev` — разные установки.
   Фиксированные hostname/пути школьных backup-установщиков и границы переноса
   приведены в [документе33](33-SCHOOL-YANDEX-RESTORE-1PANEL-QUICK-COMMANDS.md);
   обычная установка Ubuntu не настраивает эту роль автоматически.
2. Используйте принятый выпуск asa-lab и его
   [единый менеджер](https://github.com/spikeal8-maker/asa-lab/blob/main/docs/deployment/PORTABLE_OPERATIONS.md).
   Для готового выпуска нужны зелёный CI точного SHA, опубликованный манифест и неизменяемые образы.
   Проверьте применимые deployment blockers в `docs/execution/current.yaml` до обновления.
3. Восстановление старых данных сначала проверяется в новой отдельной БД с суффиксом `_test`.
   Рабочая PostgreSQL не подменяется проверочной копией. Сохраняются прежние настройки,
   ключи, имя проекта, volumes и возможность отката. Сверяются версии API/Web/Scratch и схема.
4. После допуска обновлятора ASA Lab подключите постоянную команду и школьную
   квитанцию GFS по [инструкции ASA Lab](https://github.com/spikeal8-maker/asa-lab/pull/1058),
   затем примените [меню 1Panel](33-SCHOOL-YANDEX-RESTORE-1PANEL-QUICK-COMMANDS.md).
   Терминал и панель вызывают один менеджер. Обычный порядок — `sudo asa check`,
   затем допущенный `sudo asa update`.
5. Настройте резервное копирование отдельно от расписания обновлений. Текущий
   школьный GFS делает копию PostgreSQL каждый час и полную копию в 00:20 МСК.
   Состояние и расписание на новом хосте проверьте через `sudo asa-school-gfs status`.
   Полную ручную копию можно сделать в любое время через меню. Она может кратко
   приостановить работу приложения.

## Постоянный сбор журналов

После включения соответствующего принятого исходного среза используйте официальный
`tools/log_collector.py`, а не самодельный цикл из терминала. В root-operated Linux:

```sh
sudo python3 tools/log_collector.py prepare --root /srv/asa-lab --profile production --mode system-root --reader-gid 1000
sudo python3 tools/log_collector.py reconcile --root /srv/asa-lab --profile production
sudo python3 tools/log_collector.py status --root /srv/asa-lab --profile production
```

GID1000 — пример выбранной группы чтения API. На новой установке проверьте реальный
GID API; он должен быть ненулевым и отличаться от группы Docker socket.
Root-controlled checkout и родители обязательны. API не получает Docker socket или членство в docker group.
Режим сохраняется для штатных последующих обновлений. Если новая команда отсутствует,
не обходите отказ старого менеджера: сначала нужен соответствующий проверенный выпуск.

В существующую root-owned0600 `.asa/log-collector.json` добавляется раздел
`operationalSources`: version1, реальные приватные numeric origins Ollama/ComfyUI,
`providerIntervalSeconds:60`, `backupSuccessReceipt` с абсолютным путём к настоящей
квитанции проверенного backup. Пример конфигурации и закрытые поля находятся в
`asa-lab/docs/deployment/OPERATIONAL_DIAGNOSTICS.md` выбранного выпуска.
Не создавайте фиктивную успешную квитанцию; проверка backup в облаке и чтение его
локальной последней квитанции — разные доказательства.

Проверяйте свежесть каждого закреплённого обязательного источника, requiredCoverage,
ошибки/пропуски, очередь и dropped native-журнала, аудит истории, поиск контрольного
события и реальную выгрузку ZIP из админки. `coverageComplete:false` может честно
означать границу полного исторического архива; это не разрешает игнорировать missing/error.
Ротация контейнеров10m×5, host-архив и native API-хранилище имеют отдельные бюджеты.
Существующие контейнеры получают ротацию при разрешённом обычном обновлении;
ради неё нельзя чистить volumes, обнулять журналы или перезапускать общий Docker.

## Прямое подключение к GPU без домашнего Ubuntu

Школьный Linux напрямую устанавливает SSH-forward к GPU Windows внутри tailnet.
Ollama и ComfyUI работают на GPU PC с loopback endpoints11434 и8188. Приватная
связь может идти через зашифрованный relay Tailscale; это не требует третьего
компьютера и не гарантирует прямой NAT traversal или определённую задержку.

Проверенные исходные шаблоны:

- [Linux unit](../templates/school-inference/asa-inference-relay.service.in);
- [Windows Match User](../templates/school-inference/windows-sshd-match.conf.in).

Это **не установщики**. До установки оператор подставляет точные адреса вместо
`__ASA_BRIDGE_GATEWAY__` и `__ASA_GPU_TAILNET_IP__`, проверяет их и аварийный доступ.
Первый адрес — реальный gateway выбранной ASA application bridge, достижимый из API;
не `0.0.0.0`. Нельзя копировать адреса другой Docker-сети или заменять действующую
сеть установки. GPU hostname/address и pin host key задаются для конкретного PC.

На Windows нужны работающие Ollama/ComfyUI и OpenSSH, отдельный ограниченный
`asa-gpu-direct`, public-key authentication и только два PermitOpen из шаблона.
Существующая конфигурация SSH и доступ администратора сохраняются. Перед reload
проверьте `sshd -t` и подготовьте откат через независимую консоль.
Windows firewall/ACL tailnet должны разрешать только точную приватную пару
school→GPU наTCP22; глобальные VPN/firewall/DNS ограничения не отключаются.
Публичные порты Ollama, ComfyUI и SSH для этого подключения не нужны.

На Linux приватный машинный ключ находится в `/etc/asa-inference-relay/id_ed25519`,
root0600; каталог root0700. Windows получает только публичную часть, ограниченную
источником school peer и forwarding; ключ age не используется. Host key GPU
проверяется через доверенный административный канал и сохраняется в отдельном
known_hosts с alias `asa-inference-prod`. `ssh-keyscan` без независимой проверки
не подтверждает личность сервера; StrictHostKeyChecking остаётся включённым.
После проверки unit устанавливается root-owned в systemd и включается оператором.
Автозапуск GPU приложений также должен быть настроен и проверен на самой Windows;
этот Linux unit не запускает Ollama/ComfyUI и не обещает их доступность после reboot.

Проверка: API контейнер читает `/api/tags` и `/system_stats` через заданный bridge;
отдельно запрещены shell, reverse-forward и третья TCP destination. Затем выполняются
реальный текстовый ответ, поток дольше60с, сохранение истории, PNG-генерация,
очередь/cancel/retry и восстановление связи после контролируемого разрыва.
Одной проверки TCP недостаточно. При переносе того же PC в школьную LAN tailnet
identity можно сохранить; смена транспорта не требует замены PostgreSQL или ключей ASA.
При переустановке Windows заново проверяется SSH host identity и сохраняются модели/workflow.

## Выпуск и100 учеников

После резервирования и приёмки обновления сначала докажите первый вход Scratch
без Retry, save/reopen, численную работу цепи, 3D-редактирование и соответствующие
страницы Teacher/Admin/Guest. Затем выполняется одна цепочка20→50→100 на том же
краткоживущем синтетическом fixture с одинаковыми закреплёнными бюджетами и SHA.
Смешанная волна включает обычные страницы, текст и изображения одновременно.
HTTP-проверка и100 открытых браузеров — разные доказательства.
Подготовка собственной когорты описана в [документе39](39-SYNTHETIC-ACCEPTANCE-FIXTURE.md),
а учебных QA-ресурсов — в [документе40](40-SYNTHETIC-MIXED-RESOURCES.md).
Сначала подтвердите возврат AI-политики собственного QA-класса в `deny` и скрытие
собственного публичного QA-курса, затем отзовите тестовые сессии и новый QA-admin
grant. Cleanup требует ещё действующего
исходного двухчасового доступа; инструмент не продлевает его ради уборки.
По окончании и при отказе отзываются только собственные QA-сессии/новый QA-admin grant;
рабочие записи не удаляются. При ошибке сохраняются закрытый отчёт и точные версии,
а не создаётся ложный PASS или обход приёмочного порога.
