# 11. Архитектура публикации: IP, домен и офлайн-LAN

**Дата паспорта:** 19 октября 2026 года. Эта схема основана на проверке физической Ubuntu `admins-MS-7D22` и исходного кода API 1Panel **v2.3.2**. Схема новой установки считается **предварительно проверенной тестами**, а не испытанной на чистом VPS.

## Почему в действующем сервере два веб-сервера

Публичный HTTPS сначала был настроен независимым Caddy в Ubuntu, затем перенесён в OpenResty, установленный **как приложение 1Panel**. Сейчас публичные `80/443` обслуживает **только OpenResty**. Старый публичный Caddy `asa-lab-public-ip.service` остался в конфигурации systemd с включённым автозапуском, хотя служба не запущена: это **риск после перезагрузки**. Он не должен воспроизводиться на новом сервере.

Оставшийся `asa-lab-lan-https.service` — **другая функция**: локальный HTTPS на `192.168.1.115:4610`. Контейнер Web ASA Lab слушает только `127.0.0.1:4610`. Caddy заверяет локальный IP собственным офлайн CA, не публикуется на `80/443`, не конфликтует с OpenResty и позволяет работать без внешнего интернета. Сертификат локального CA требуется доверить на школьных компьютерах; для публичного браузера его использовать нельзя. Если в будущем 1Panel/OpenResty сможет обеспечить *эквивалентную автоматическую выдачу доверенного локального TLS и автономность*, локальный Caddy можно будет удалить отдельной проверенной миграцией.

## Точная схема

```text
Интернет: публичный IPv4 / будущие DNS-имена
                   |
            МТС: NAT 80, 443
                   |
  Ubuntu 192.168.1.115 / Tailscale 100.75.149.26
                   |
           1Panel OpenResty
   IP:94.29.44.211 -> сертификат для IP (ACME)
   site.<домен>    -> ОТДЕЛЬНЫЙ сертификат DNS (ACME)
                   |
              localhost:4610
                   |
             ASA Lab Web/API
                |       |
           PostgreSQL  MinIO (+ Scratch)

Офлайн-школа: https://192.168.1.115:4610
                   |
        Локальный Caddy (не публичный)
                   |
              localhost:4610

Удалённое администрирование: tailnet → SSH 22 / 1Panel 19192
                               не открывать в NAT / internet.
```

Два проекта могут использовать **один публичный IP**: по DNS-именам через SNI и HTTPS 443; либо каждый на собственном отдельном внешнем порту HTTPS. Проектам нельзя назначать один и тот же `IP:port` в нескольких процессах; OpenResty выбирает сайт по имени хоста на стандартном 443. Публичный IP не является доменным именем: сертификаты IP и DNS проверяются независимо.

## Проверенный IP, без домена

В 1Panel зарегистрирован сайт `94.29.44.211` (тип `proxy`), сертификат Let's Encrypt от 19 октября до 26 октября 2026 года, `autoRenew=true`, OpenResty слушает 80/443. Из локальной сети D2-R2 `https://94.29.44.211/health/ready` возвращал `ready` / `database=up` / `schema=213`. **Это не доказывает** проход из любой внешней сети, автопродление и работу входа/сохранения.

### Новый домен: полностью проверяемый процесс

1. Получить или делегировать домен в DNS-регистраторе. Для отдельного проекта удобнее субдомен: например, `lab.alikinas.ru` (именно *пример*; не использовать, пока владелец не подтвердит выбор). У DNS A должен быть адрес актуального внешнего IPv4. Если сервер за CGNAT, прямое подключение и HTTP-01 не заработают: нужен внешний VPS/reverse ingress и отдельная согласованная архитектура.
2. Настроить NAT роутера **только 80 и 443 → 192.168.1.115**. Не открывать 22, 19192, 4610, 5432, 9000, 39443. Для VPS правила безопасности применяются в firewall провайдера и UFW.
3. Если у DNS имени есть AAAA, обеспечить правильный IPv6 и его ingress либо убрать неверную AAAA: иначе некоторые клиенты/ACME попадут не туда.
4. **До публикации домена** подготовить и согласованно проверить разрешённый HTTPS origin в ASA Lab (`/srv/asa-lab/.env`, `docs/deployment`, issue ASA Lab #584). Не отключать CSRF/проверку origin ради HTTP 200. Изменения переменных приложения и рестарт — в процессе релиза ASA Lab, а не через конфиг 1Panel.
5. Проверить план (эта команда **ничего не меняет**, домен можно указать фактический после выбора):

```bash
python3 scripts/domainctl.py plan --domain lab.alikinas.ru --public-ip 94.29.44.211
```

6. Только после бэкапа, исправных DNS/80/443, подтверждения origin и подключения API-ключа к localhost 1Panel:

```bash
sudo python3 scripts/domainctl.py apply --domain lab.alikinas.ru --public-ip 94.29.44.211 --origin-prepared
```

`domainctl.py` проверит A/AAAA, backend и БД, наличие ACME-аккаунта Let's Encrypt, создаст **отдельный** proxy-сайт в 1Panel (не редактируя рабочий IP-сайт), создаст сертификат с `autoRenew=true`, дождётся `ready` и подключит TLS через штатный `/websites/:id/https` с HTTP→HTTPS. Если сертификат уже существует, но не готов, или сайт уже занят другим проектом, произойдёт безопасный STOP без перезаписи. Задача проверки может потребовать отдельного ручного этапа из-за неготового origin или DNS.

**Ограничение:** код API предназначен именно для 1Panel v2.3.2 и не прошёл полный интеграционный прогон создания нового сайта на отдельном сервере. После каждой операции требуется проверка сайта с независимого клиента, конкретных статусов сертификата и сквозной авторизации/сохранения в ASA Lab. Повторный запуск для уже существующего сайта не изменяет его без проверки.

## Автоматический второй этап после установки 1Panel и ASA Lab

Базовую установку выполняет `sudo bash install.sh --profile home-static --apply`. Далее владелец авторизует Tailscale, настраивает 1Panel и сохраняет API-ключ в root-only файл. Приложение ASA Lab и локальную PostgreSQL/MinIO восстанавливают собственными процедурами проекта, **не создавая пустую БД**, и только затем запускают второй этап. Команда плана:

```bash
bash scripts/edge-setup.sh --profile home-static --public-ip 94.29.44.211 --lan-ip 192.168.1.115 --lan-cidr 192.168.1.0/24 --lan-https
```

Команда применения (только **новый** подготовленный сервер с уже готовой базой):

```bash
sudo bash scripts/edge-setup.sh --profile home-static --public-ip 94.29.44.211 --lan-ip 192.168.1.115 --lan-cidr 192.168.1.0/24 --lan-https --origin-prepared --apply
```

При новом развертывании без IP-сайта второй этап автоматически создаёт IP-сайт, заказывает **короткоживущий IP-сертификат** через 1Panel (HTTP-01, isIp=true), включает autoRenew и HTTPS после подтверждения готовности. Рабочий существующий IP-сайт не перезаписывается. Ключевое ограничение: должно быть заранее подтверждено, что ASA Lab допускает https-origin IP; параметр `--origin-prepared` обязателен.

Добавление домена к тому же backend: аргументы `--domain lab.alikinas.ru --origin-prepared` при заданном `--public-ip`. При наличии IP-сайта этот сценарий его сохраняет; новый SNI-vhost добавляется отдельно. По умолчанию второй этап также ставит **локальный MCP в режиме readonly** на `127.0.0.1:39443` и **systemd-монитор SSL** каждые шесть часов для заданного публичного IP. Для отдельной диагностической установки предусмотрены флаги `--no-mcp` и `--no-cert-monitor`. Монитор только записывает предупреждения в журнал; внешние уведомления пока не подключены.

**В профиле home-dynamic/CGNAT автоматическое публичное создание домена запрещено**, пока не спроектирован VPS tunnel.

## Локальный HTTPS для школы

`scripts/lan-https.sh` применяют только на новом сервере, где ещё нет отдельной LAN-Caddy службы. Он устанавливает Caddy из подписанного APT-репозитория Ubuntu (версию нужно зафиксировать в отчёте исполнения), маскирует стандартный публичный Caddy-сервис, создаёт только LAN-конфиг `https://LAN_IP:4610`, `systemd` и узкое правило UFW (`--lan-cidr`). Если LAN IP/порт уже занят другим приложением, бэкенд не отвечает или старый публичный Caddy обнаружен, запуск останавливается. Корневой ключ локального Caddy CA остаётся в защищённом каталоге Ubuntu; **в Git он не помещается**.

Параметры внутренней TLS-системы следует считать частью переносимой конфигурации. Конфигурацию можно восстановить декларативно, а доверие школьных клиентов/локальную CA следует восстанавливать по защищённому архиву или заново распространять CA; приватный корневой ключ CA не публикуется в Git.

## Приёмка, прежде чем удалять старый Caddy

- Доказать принадлежность 80/443 только OpenResty; 1Panel отображает сайт, сертификат и автопродление.
- Проверить `192.168.1.115:4610` из LAN и отключить интернет на испытательном клиенте, удостовериться в запуске, сохранении и открытии проектов ASA Lab.
- Сделать backup systemd, текущего Caddyfile, CA и конфигурации; убедиться, что локальная TLS доверена клиентами.
- Если иной LAN ingress из 1Panel предоставляет тот же HTTPS и офлайн-функцию, проверить его на отдельном порту, затем переключить клиентов и только после этого отключать LAN Caddy.
- Старую публичную службу `asa-lab-public-ip.service` разрешено **только disable** после отдельного снимка, подтверждения, что она inactive и OpenResty держит 80/443; документы о rollback сохраняются. Удалять её конфиг немедленно необязательно.
