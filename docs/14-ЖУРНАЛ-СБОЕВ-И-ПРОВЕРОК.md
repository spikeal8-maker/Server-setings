## Почему возникли проблемы (без предположений, которые выдают за факт)

1. **«Почему два веб-сервера?»** История переезда: публичный сайт сначала опубликовали через отдельный Caddy в Ubuntu, затем OpenResty через 1Panel. Старый публичный Caddy выключен; LAN Caddy ещё нужен. Схема не должна плодить новые службы.
2. **«Почему ключ работает, а ChatGPT не подключается?»** Ключ действительно подписывает запросы 1Panel API с D2-R2; **MCP — другой протокол и другой публичный HTTPS endpoint**, который пока отсутствует. Официальный `mcp-1panel` предоставляет Bearer в собственном HTTP режиме, а UI ChatGPT для custom MCP требует поддерживаемую регистрацию и OAuth (или публичные anonymous операции, что неприемлемо для админ-доступа). См. Issue #9.
3. **«Почему невозможен апдейт ASA Lab?»** Менеджер опубликованных релизов останавливается из-за состояния `synchronized=null`; простое Docker `healthy` этого не заменяет. Не подделывать health, не менять целевую DB/schema вручную.
4. **«Почему CI сначала было FAIL?»** У PR #6 ранние jobs имели 0 steps из-за ограничения billing/расходов GitHub. После перехода репозитория в public повторение exact-SHA `39269383572` SUCCESS. Это решило CI-блокер, не интеграционную установку.
5. **«Почему нужен OAuth?»** ChatGPT должен отдельно удостоверять личность владельца при работе с защищёнными инструментами MCP. Статический ключ 1Panel административный; выдавать весь ключ в общедоступный reverse-proxy и считать его OAuth нельзя.

## Протокол для нового бота с нулевым контекстом

1. Прочитай `README.md`, `AGENTS.md`, документы 13 и 14, Issues #9/#4/#3/#2 и PR #5/#6; для обновления ASA Lab — Issue #620.
2. На момент нового сеанса **сверь HEAD в GitHub**, действующие API/1Panel данные и время; исторический чекпоинт не равен текущему состоянию. Важна чёткая маркировка `PASS`, `FAIL`, `UNKNOWN`, `BLOCKED`.
3. Для ChatGPT MCP отличай три независимых факта: **API 1Panel отвечает** / **MCP сервер работает на Ubuntu** / **ChatGPT реально обнаруживает и вызывает инструменты**. Только последнее даёт владельцу требуемый результат.
4. Пользователь не хочет команды для ручного ввода; предпочитай управление через UI 1Panel и ChatGPT Plugins. Если для сборки нужен код — автоматизируй и публикуй его в GitHub, но не выдавай длинные терминальные команды владельцу.
5. Документируй изменения с SHA, дельтами, neg/pos проверками, режимом доступа, датами, ссылками на CI и обратимым планом. Секреты в public repo и истории Git категорически запрещены.
6. Вносить изменения на **работающий** тестовый сервер только после health/backup/rollback и проверки, что не затрагиваются ученики, классы, проекты и база.
