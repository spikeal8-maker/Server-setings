# 15. Новые домены ASA Lab: почему открывается вход, но авторизация не работает

**Дата инцидента:** 20.10.2026. **Источник:** https://github.com/spikeal8-maker/asa-lab/issues/646

## Что произошло на настоящем тестовом сервере

В 1Panel добавлен HTTPS-сайт `test.asa-lab.ru` с обратным прокси `/ → http://127.0.0.1:4610`. Главная страница и форма авторизации открывались. Но API отклонял POST-вход, поскольку новый домен отсутствовал в явно настроенном `ASA_PUBLIC_WEB_ORIGINS`. Внешний интерфейс выводил неопределённое сообщение «Ошибка сервера. Попробуйте ещё раз».

Точный механизм расположен в `asa-lab/apps/api/src/origin-policy.ts` и `app.factory.ts`: защищённые POST/PUT/PATCH/DELETE запросы принимаются только от **явно разрешённых HTTPS Origin**. Это осознанная защита CSRF. **Запрещено отключать проверку, доверять всем Host, ставить "*" или разрешать HTTP.**

До ремонта `POST /api/auth/login` с `Origin: https://test.asa-lab.ru` возвращал **HTTP 403 `origin_forbidden`**. После добавления точного домена и выборочного пересоздания только API ответом на безопасный тестовый пустой JSON стало **403 `bot_check_required`**. Это доказывает прохождение origin policy, но ещё не доказывает реальный вход с паролем.

## Порядок подключения ЛЮБОГО нового домена

1. Выяснить, относится ли домен именно к ASA Lab (у proxy должно быть `/ → http://127.0.0.1:4610`). Если это отдельный проект, **не добавлять его Origin** в ASA Lab.
2. В 1Panel проверить DNS/A/AAAA, HTTPS-сертификат и проверку доверия браузера. Не считать статус Running доказательством работы входа.
3. **До публикации домена** выполнить `python3 scripts/check-asa-domain-origins.py --domain test.asa-lab.ru` из безопасного окружения (по умолчанию читает `/srv/asa-lab/.env`), либо автосверку `--discover-1panel --api-key-file <защищённый локальный файл>`. Ни один режим не изменяет настройки.
4. При `FAIL` согласовать домен с владельцем и добавить его к `ASA_PUBLIC_WEB_ORIGINS` как полный origin: `https://имя-домена`. Сохранить ранее разрешённые школьный HTTPS/IP. Не допускать более восьми записей.
5. Сохранить резервную копию конфигурации в защищённом хранилище. Обновить `.env` через «Файлы» 1Panel или штатный API `/api/v2/files/save`. **Работающий API не читает изменения `.env` до пересоздания контейнера.**
6. Для опубликованного release проверить **точный digest** запущенного API-образа в 1Panel. Обычный `docker compose config --images` может показывать `asa-lab-api:local`, хотя живой API использует образ из GHCR. Запрещено вслепую делать `compose up` всего стека или менять релизный образ на локальный.
7. Проводить `docker compose --dry-run` с закреплённым образом, `--no-deps --no-build --pull never --force-recreate api`. Продолжать только если план показывает **только API**. Затем выполнить выборочное пересоздание API с тем же digest; миграции, PostgreSQL, MinIO, Scratch, Web не трогать.
8. Проверить `GET /health/ready` и основной сайт по старому IP, новому домену, школьному адресу. С обоих разрешённых публичных Origin безопасный тест `POST /api/auth/login` с пустым JSON не должен возвращать `origin_forbidden`; посторонний Origin **обязан** возвращать `403 origin_forbidden`.
9. Владелец проверяет **настоящий вход тестовой учётной записью**, сохранение HttpOnly/Secure cookie, обновление сессии и выход. Пароли в GitHub/логи не отправлять. Проверить Classroom/Scratch, если домен используется на занятии.
10. Закрывать issue только после e2e login PASS; записать SHA образа, время, точный список Origin, результаты, rollback. Отправить актуальный паспорт в Server-setings.

## Автоматическая проверка через API 1Panel

`scripts/check-asa-domain-origins.py` умеет находить HTTPS-сайты 1Panel с действующим root reverse proxy к ASA Lab и сверять их с `ASA_PUBLIC_WEB_ORIGINS`. Программа **только читает** конфигурации, ничего не добавляет, не перезапускает и не публикует ключи. Запускается на Ubuntu под контролем оператора; файл API-ключа должен иметь права не шире 0600.

Пример явной проверки любого будущего домена: `python3 scripts/check-asa-domain-origins.py --domain test.asa-lab.ru`.

Автопоиск сайтов, указывающих на ASA Lab: `python3 scripts/check-asa-domain-origins.py --discover-1panel --api-key-file /var/lib/server-settings/1panel-api.key` — только если соответствующий защищённый файл действительно создан владельцем. Не создавать пустые файлы-заглушки и не использовать тестовый пароль в исходниках.

**Важно:** primaryDomain покрывает основной домен в 1Panel. Если к сайту добавлены дополнительные alias-домены, их надо также перечислить как отдельные `--domain` или расширить проверку чтением доменных связок 1Panel. Автоматически разрешать весь набор `Host` нельзя.

## Контроль и откат

- До обновления `.env` зафиксировать текущую точную строку и digest живого API.
- При ухудшении исправить конфигурацию обратным изменением через 1Panel и пересоздать только API на **том же закреплённом образе**.
- Проверить, что PostgreSQL/MinIO не тронуты, Web/Scratch не перезапускались, на старом IP вход работает.
- `origin_forbidden` для нового домена после правки означает прежде всего, что API не получил обновлённую переменную, что DNS/proxy ведёт на другой backend или что Origin отличен от точного значения. Не удалять защиту CSRF.
- Веб-ошибку «Ошибка сервера» при коде `origin_forbidden` следует улучшить отдельным изменением продукта ASA Lab с понятным кодом для технической поддержки.
