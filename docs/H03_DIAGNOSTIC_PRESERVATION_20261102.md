# Сохранение диагностической истории H03

Проверки выполнены на исходном тестовом Ubuntu `admins-MS-7D22`, в существующей
установке `/srv/asa-lab`, Docker project `asa-lab-dev`. Вход —
`https://test.asa-lab.ru`. Школьная VM100 — отдельная установка, а её обновление
и приёмка требуют отдельного прогона.

## Подтверждённый результат

2 ноября 2026 года, 20:36:16–20:36:19 UTC, создана защищённая forensic-копия
host-сборщика: **1 403 исходных файла, 131 882 395 байт**. Сборщик кратко
приостановлен и возобновлён в прежнем USER manager. Службы приложения,
PostgreSQL и MinIO эта операция не переключала.

Инструмент из [PR52](https://github.com/spikeal8-maker/Server-setings/pull/52),
точный source `6b0eb3d56acd829dc14891924cc63ff5bb163d73`, предварительно прошёл
независимое review, 18 Linux-тестов без пропусков на H03 и чтение состояния
реальной службы. Исправление `loginctl` проверено реальной командой; успешный
mock-тест прежней версии не выдаётся за доказательство этого поведения.

Независимая проверка сохранённого набора подтвердила все 1 407 файлов из таблицы
копий манифеста, закрытые права 0600/0700, владельца root, отсутствие ссылок и
два SQLite `quick_check` через `mode=ro&immutable=1`. SHA256 манифеста:
`eccb0bf480fd636f1d527da4a4b78e024668d2f4e34dbc8e6f600d25481889d5`.

Данные независимого native-журнала `.asa/diagnostics/application` находятся вне
scope этой host-копии. Набор файлов, включая локальный служебный ключ проверки
сегментов, остаётся на сервере в защищённом хранении. В GitHub публикуются
только закрытые счётчики и квитанции.

## Что ещё не исправлено

Копия сохраняет **31 проблемный retired-сегмент** и статус
`NOT_A_VERIFIED_RECOVERY_SNAPSHOT`. Она не объявляется восстановленной
диагностической историей. Постоянный host-сбор пока не восстановлен.

В сохранённом наборе найдена проверяемая опора для узкого восстановления:
все **607 уникальных событий** этих файлов опубликованы в одном другом
сегменте и точно совпадают как JSON и как исходные JSONL-строки. Его существующая
HMAC-квитанция, фактические compressed/raw SHA256 и полный current sequence/ID
mapping проверены. Отсутствующих, неоднозначных и unpublished записей нет.
Новые «старые» HMAC не создавались.

Обнаруженная причина: compaction сохраняет retirement/remapping, но не
сохраняет проверенные original metadata в той же durable-транзакции. Следующий
срез — устранить это окно и проверить явный typed successor-proof recovery
сначала в отдельной копии. Реальный recovery пока **NOT_RUN**.
