## Полномочия бота

В существующее подключение добавлены:

- `asa_host_inventory` — фактические контейнеры и метаданные узла без environment;
- `asa_admin_execute` — произвольная Bash-команда **с правами root всего тестового узла**: Git, Docker/Compose, сборки, файлы, службы и восстановление;
- `asa_admin_status` — состояние привилегированного исполнителя и независимый root-аудит задания;
- `asa_cloud_transfer` — общий транспорт зашифрованных архивов через Docker/Яндекс.Диск.

Это полномочия root, а не allowlist нескольких команд. Такой инструмент позволяет обойти gates обычного обновления и удалить данные. Штатные `asa_update_plan/start` сохраняют свои проверки, но они не являются ограничением произвольного root-инструмента. Для обычного выпуска предпочтителен штатный цикл с backup/миграциями/приёмкой. Возможность команд сборки не означает, что любое состояние main уже собрано и принято.

Пример диагностики:

```json
{
  "installation_id": "asa-test",
  "command": "id; docker compose version; docker ps --format '{{.Names}} {{.Status}}'",
  "cwd": "/srv/asa-lab",
  "timeout_seconds": 60,
  "idempotency_key": "diagnostic-unique-request-001"
}
```

Команда возвращает `operation_id` сразу; состояние/результат читаются `asa_operation_get`. При потерянном ответе повторяется **тот же** idempotency key. Операции сериализованы с обычными update/restore. Команды не получают автоматического backup или rollback. Рабочий каталог по умолчанию — ASA root; timeout по умолчанию 3600, максимум 7200 секунд.

Привилегии включаются владельцем отдельно: backend по-прежнему работает как `admins`, а root-исполнитель использует private Unix socket `0600` и root-owned конфигурацию. Проверяются UID вызывающего процесса, hostname и UUID установки одновременно в запросе, root-конфигурации и текущей установке. Root-аудит синхронизируется на диск до исполнения и запрещает повтор команды после разрыва. Код запускается Python `-I` без импорта приложения из writable checkout. Это trusted root administration, не песочница для недоверенного кода.

Сырые журналы — root-only, до 8MiB; MCP получает до 32KiB вывода с редактированием известных буквальных секретов. Редактирование не гарантирует обнаружение преобразованных или неизвестных секретов: не помещать пароли в команды и не выводить credentials. Root socket не публикуется в интернете. Existing HTTPS/OAuth сохраняется; unauthenticated запросы не получают доступ.

Живой proof `bc6f36978401444d8895f7787fbba36f`: команда через MCP получила UID0, создала/удалила собственный root-файл с владельцем0 и режимом600, выполнила Docker CLI. Повтор был reused без повторного исполнения. Пользователь `nobody` не смог подключиться к socket. Обычный сервис MCP может читать root-owned policy через группу (`0640`), но не менять её; root executor config — `0600`.

Владелец отдельно подтвердил обновление инструментов ChatGPT. После обновления интерфейс приложения реально показывает **Write11 + Read12 = 23** и новые команды. Режим приложения «Разрешать все действия» сохранён. Старые 17 инструментов не являются текущим серверным набором; уже открытый чат может сохранять свою первоначальную tool context до следующего запроса/нового чата.

## Воспроизводимая установка расширения

Использовать проверенный source из этого репозитория, private `asa-operations.json/.env` и существующий MCP backend. Сначала тесты и независимое ревью точного SHA. Команды без `--apply` показывают только план:

```bash
python3 scripts/enable-asa-host-admin.py
sudo python3 scripts/enable-asa-host-admin.py --apply --enable-full-admin --expected-host ACTUAL_HOSTNAME
python3 scripts/install-cloud-storage.py
sudo python3 scripts/install-cloud-storage.py --apply --expected-host ACTUAL_HOSTNAME
```

На другой машине требуется отдельное решение владельца о полном root-доступе и её реальный hostname/installation UUID. Установщик отказывается работать при активной/неразобранной операции. Он обновляет только MCP/backend и своё облачное приложение; не переустанавливает Docker/1Panel и не очищает данные ASA.

Rollback полномочий: сначала выставить `host_admin_enabled=false` и `cloud_storage_enabled=false` в root-controlled backend policy с сохранением чтения группой, перезапустить только `asa-operations.service`, остановить/отключить `asa-admin-executor.socket` и обновить инструменты клиента. Не удалять аудит и не прерывать активное задание вслепую. Предыдущий код и policy сохранены приватно на сервере; backup приложения — отдельно от rollback кода MCP.

## Общее хранилище нескольких проектов

Контейнер `asa-cloud-storage-rclone-1`, официальный rclone1.75.2 с digest `sha256:2687085f718d3c628f7fdfb77c52a1d344332aed543110bb88088f2c70d43eb5`. Root directory `/srv/asa-cloud-storage` приватный; credentials в `config/rclone.conf`, spool в `data/`. Контейнер работает UID1000, read-only filesystem/cap-drop, не получает Docker socket, PostgreSQL volume или публичные порты. Его RC слушает только loopback **внутри контейнера**.

Пространства: проект `asa-lab` использует прежнюю `ASA-Backups`; другие project slugs — `Server-Backups/<project>`. Upload читает `data/<project>/outgoing/<file>.age`, download создаёт только новый файл в `incoming/`. Существующий файл не перезаписывается; удаление/mirror отсутствуют. Upload использует immutable/checksum и проверяет age-header; это распознавание формата, а не криптографическая проверка всего архива. Optional `sha256` сверяет скачанные/отправляемые байты. Перед восстановлением отдельно проверяются комплект, ключи, совместимость и явная целевая БД.

```json
{
  "installation_id": "asa-test",
  "action": "download",
  "project": "asa-lab",
  "filename": "EXACT-VERIFIED-BACKUP.tar.age",
  "sha256": "EXPECTED_64_HEX_CHARACTERS",
  "idempotency_key": "cloud-download-unique-request-001"
}
```

Получение архива не означает переключение рабочей базы. Расписание резервирования пока не включено. Приватный age identity владельца остаётся вне сервера; серверу для будущего шифрования достаточно public recipient.

### Текущий статус Яндекса

Контейнер установлен и healthy. Владелец выполнил стандартную OAuth-авторизацию rclone; token сохранён приватно, без значений в GitHub/чате. Но quota API отвечает200, а операции `/resources` —410 GoneError: это воспроизведено прямым REST-запросом и rclone. Наличие token **не выдано за рабочий файловый доступ**; status сообщает `connected=false`, `CLOUD_PROVIDER_GONE`.

Та же неисправность общего клиента описана в [rclone issue10067](https://github.com/rclone/rclone/issues/10067). [Документация Яндекса](https://yandex.com/dev/id/doc/ru/register-api) разрешает собственное OAuth-приложение для API. Для этого подготовлена форма `ASA Lab Server Backups` с disk.read/write/info в аккаунте владельца; создание и авторизация ожидают отдельного подтверждения. Ни чужие токены, ни cookie/session credentials не используются.

Проверка encrypted upload/download и совпадения SHA256 **пока не принята**. Подготовлен маленький зашифрованный TEST marker, не рабочая БД; он ещё не загружен в облако. Полная успешность хранилища будет записана только после фактической передачи в обе стороны. Основная задача обновления ASA и полный root MCP уже выполнены независимо от этой внешней блокировки.
