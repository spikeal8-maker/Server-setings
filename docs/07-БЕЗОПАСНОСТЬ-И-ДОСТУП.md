# 7. Безопасная сеть и администрирование

## Защитный периметр

**Опубликованы** только веб-порты проектов 80/443, если они нужны профилю. LAN/SSH: 22 (на другом VPS может быть 2221); панель: 19192 из доверенных LAN/Tailscale; Docker Web ASA Lab: 4610 только на `127.0.0.1` плюс выделенный LAN Caddy. MCP: 39443 только на 127.0.0.1. PostgreSQL 5432 и MinIO 9000 никогда не должны принимать WAN.

На тестовой Ubuntu UFW уже включён, `default deny incoming`, `allow outgoing`; SSH и 1Panel допускаются через `192.168.1.0/24` и `tailscale0`. На **новом** сервере список LAN и доверенных CIDR задаётся профилем и текущим клиентом SSH. Замените локальные сети в профилях при другой LAN (например, если там 10.0.0.0/24). Не используйте роутер NAT для панели, базы, Docker API и MCP.

### Шаги безопасного изменения UFW

1. Убедитесь, что у вас есть второй канал связи: консоль/VNC/Tailscale либо физический доступ.
2. Выполните `python3 scripts/serverctl.py plan --profile vps` и убедитесь, что ваш текущий SSH IP/порт добавлены в allowlist.
3. Введите `--admin-cidr` для другого доверенного источника, если он нужен.
4. Выполните `sudo bash install.sh ... --apply` только на чистой Ubuntu. На существующем сервере изменения проводите отдельно после снимка.
5. До выхода из текущего сеанса откройте **новое** SSH-подключение, затем проверьте `sudo ufw status numbered`, `ss -lntp` и `tailscale status`.

### Статический и динамический WAN

Статический публичный IP **не обязателен** для приватного удалённого управления через tailnet. Если CGNAT, роутер не принимает входящие соединения без внешнего входного узла, поэтому публикация сайтов требует DDNS (только при белом IP) или отдельного согласованного туннеля/VPS. Локальная ASA Lab должна оставаться работоспособной без интернета, а PostgreSQL — локальным.

### Дополнительные меры

SSH-ключи вместо общего пароля, 2FA для 1Panel, обновления безопасности Ubuntu, резервный канал связи, разделение операторских/API прав, аудит изменений, проверка обновления короткоживущего сертификата. **Нельзя** отключать CSRF, origin checks, блокировку роботов или HSTS ради того, чтобы получить HTTP 200. Автоматическую смену SSH-портов и отключение password auth включайте только после ручной проверки ключевого входа.
