# 6. Восстановление, защита данных и резервные копии

Здесь три **независимых** вида данных: (1) конфигурация ОС/1Panel/OpenResty, (2) PostgreSQL + MinIO + проекты ASA Lab, (3) секреты, Tailscale identity и сертификаты. Копия (1) не заменяет (2); копия GitHub-репозитория не заменяет (1) и (3).

## Конфигурация сервера — age

Установите `age` из доверенного репозитория ОС (`sudo apt-get install age`). На личной машине создайте age identity и **держите приватный файл вне сервера и GitHub**. На Ubuntu сохраняется только публичный адрес получателя `age1...` в `/etc/server-settings/age-recipients.txt`; каталог `/etc/server-settings` root-only.

```bash
sudo bash scripts/backup-settings.sh
sudo bash scripts/backup-settings.sh --apply
```

При `--apply` скрипт снимает консистентные SQLite-снимки `core.db`, `agent.db`, `xpack.db` через SQLite Backup API; архивирует выбранные каталоги с конфигурацией 1Panel, OpenResty, UFW, systemd, LAN Caddy и шифрует через `age -R` в `/var/backups/server-settings`. Имя включает UTC timestamp; к зашифрованному архиву формируется `.sha256`. Весь набор необходимо регулярно переносить в **другое хранилище**: дисковый сбой может уничтожить и сервер, и локальный backup.

**Ограничение:** работающая 1Panel содержит и другие связанные компоненты (Docker image/volume, runtime и приложение из магазина), которых в снимке конфигурации может не быть. Для полного disaster recovery нужен отдельный штатный 1Panel snapshot, полный список зависимостей и практическая проверка восстановления на выделенном тестовом сервере. Ключи шифрования, Tailscale-состояние и закрытые CA-сертификаты обрабатывайте отдельно.

## ASA Lab — другой контур

Рабочие данные тестовой Ubuntu были восстановлены ранее из проверенного зашифрованного архива; после последнего аудита обнаружена директория `/srv/asa-restore/20261017T231505Z-65b68074`. Она **не доказана** как самая свежая или восстановимая копия. Не переписывайте живую БД без проверки нового архива, согласованной резервной точки и счётчиков данных.

Репозиторий приложения: https://github.com/spikeal8-maker/asa-lab

* Не создавать пустой production PostgreSQL при переносе, если есть проверенный snapshot.
* Основной Compose project — **`asa-lab-dev`**: переименование проекта/томов может отключить реальные данные.
* Использовать собственные `tools/bootstrap/prepare-age-backup.py`, `tools/bootstrap/restore-verified-backup.py` из согласованного состояния GitHub, а не произвольный `docker compose down -v`.
* Scratch, API, MinIO и PostgreSQL проверяются после восстановления отдельно через backend/frontend/e2e, а не одним HTTP 200.
* Зашифрованные архивы Яндекс Диска принадлежат контуру резервирования ASA Lab. Не хранить рабочие файлы PostgreSQL непосредственно в синхронизируемой папке.

## Приёмка восстановления

Проверяется на **отдельном узле**: hash архива → age расшифрование → конфигурация/версии → Docker/1Panel → HTTP/HTTPS → API/база/проекты/сохранение → изолированная перезагрузка → повторная проверка. После успешной репетиции фиксируются точные команды, SHA и дата. Не заменять рабочие конфигурации на сетевом сервере ради теста.
