## Исходное состояние и правило записи

До перехода **H04 — единственный источник production-записей**. Школьный
`https://x.asa-lab.ru` — копия для подготовки и собственных QA-проверок.
В окне финального переноса production-запись закрыта на обоих узлах;
после переключения её принимает только школа. Старый маршрут и клиенты
с прежним DNS не должны снова открывать запись на H04.

В школе принят `asa-lab-school` на `asa-school-01`/VM100:
`3e8713476cafedda3e24a39665458e833efd7c22`, schema307, live OID117178.
Это **ещё не финальный срез H04 после остановки записи**; последующие
собственные QA-записи учитываются отдельно.
[Квитанция принятого refresh](../snapshots/2026-11-08/school-xprep04-v5-refresh-accepted-exact-20261108.json).

Семь полей шифрования данных/keyrings и две S3 credentials source/school
[сверены в02F](../snapshots/2026-11-08/school-x-prep02f-readonly-20261108T002602Z.json).
Служебные пароли БД, ключ подписи Blocks и search secret у школы отдельные:
весь школьный env на H04 env не заменять, ключи шифрования данных заново
не генерировать. Финальный архив проверяется повторно по своему manifest.

**Решение о сессиях до окна:** базовый вариант плана — управляемый повторный
вход по перенесённым аккаунтам и ученическим кодам; заранее сообщить порядок
пользователям. Автоматический перенос действующих H04-сессий не доказан.
Бесшовный вход нельзя обещать на основании совпадения ключей данных или counts.

## Порядок перехода

Один бот выполняет один ограниченный этап; контролёр сверяет фактический
результат и фиксирует его. Следующий шаг опирается на завершённую квитанцию,
а не на отсутствие ошибки в чате.

1. **Завершить приёмку X.** Получить принятые UI-сценарии, ступенчатую HTTP-нагрузку,
   новую школьную копию с decrypt/изолированным PG+MinIO restore и проверку
   authenticated logging API. Закрепить фактический release/manifest/images
   и schema307. Обновление выпуска не смешивать с финальным переносом данных.
2. **Подготовить окно и возврат.** Зафиксировать действующие H04 и школьные
   установки, актуальные ingress/DNS/TLS/public origins, маршруты и закрытые
   копии конфигурации. Сохранить H04, архивы и школьное состояние до замены.
   Для каждого сохраняемого состояния записать фактические время, OID и SHA
   после получения; существующий old OID26362 не подставлять вместо будущего
   состояния этого окна. Согласовать окно запрета записи и повторного входа.
3. **Остановить production-запись на H04 и получить финальную копию.** Проверить
   прекращение пользовательских и фоновых writers; сделать согласованный
   canonical export PostgreSQL + объектов MinIO + необходимой закрытой
   конфигурации. Проверить полный manifest/инвентарь, источник, версию и схему.
   Зашифровать архив, сохранить на Яндекс Диск, скачать обратно, сверить SHA,
   расшифровать внешним ключом и повторно проверить содержимое. Одного cloud
   SHA недостаточно. После завершения backup H04 должен оставаться без новых
   записей: если они появились, финальный срез получить заново.
4. **Перенести именно финальный срез в школу.** Повторно сверить data keys/S3
   credentials и школьные служебные настройки. Проверить восстановление БД,
   миграции до закреплённой схемы, ACL/RLS и объекты на реальном целевом MinIO;
   затем выполнить ограниченный refresh школы с сохранением состояния до него.
   Принять фактические routing/OID, данные, file hashes, S3 list/чтение и health.
   H04 и его согласованная копия остаются сохранёнными, production-запись закрыта.
5. **Проверить будущий публичный вход до открытия production-записи.** Для
   `https://asa-lab.ru` подготовить проверяемый маршрут в фактическом ingress
   и проверить его контролируемым клиентом с правильными hostname/SNI, без
   общего переключения DNS. Проверки ниже сначала провести на X, затем на
   этом маршруте. Не отключать TLS/CSRF/origin-проверки ради успешного теста.
   Любую школьную запись, включая QA/сессии, учитывать при выборе сценария возврата.
6. **По отдельной инструкции выполнить cutover.** Переключить production-маршрут
   и разрешить запись только в школе. H04 оставить закрытым для записи;
   учитывать старые DNS-кэши. С внешнего клиента повторить приёмку уже по
   обычному `https://asa-lab.ru`, отметить первую школьную запись и начало
   наблюдения. SMTP/боты не включать, пока школа остаётся тестовой копией;
   их активация после перехода — отдельная ограниченная настройка. ИИ/VPN позже.
7. **Закрепить результат.** Проверить ошибки, сохранение новых проектов,
   свежесть журналов и новую резервную копию рабочего состояния. H04, прежние
   архивы и журналы не очищать в ходе перехода. После каждого принятого этапа
   обновить [матрицу](08-ПРОВЕРКИ-И-ОГРАНИЧЕНИЯ.md), safe receipts и
   [таблицу оборудования](https://docs.google.com/spreadsheets/d/12VHlK1sko6g8T_xn_13jjQd_USFkW7tlV73yMRhAjwE/edit#gid=500):
   результат, ограничения, следующий шаг; секреты — только custody/path.

## Что считается приёмкой публичного входа

- Точный HTTPS URI, доверенный сертификат/hostname/SNI, корректные redirects,
  `/health/ready` с нужной версией и схемой; API, WebSocket и assets действительно
  работают. Один HTML200 или Docker healthy этого не подтверждает.
- Штатный вход преподавателя и ученика, границы ролей, открытие курса и проекта;
  edit → save → повторное открытие в новом контексте для Scratch, 3D/Electronics,
  чтение сохранённых assets/файлов. Административные проверки — существующим
  разрешённым доступом, без выдачи нового admin обычному QA-преподавателю.
- Нагрузка по закреплённому профилю до **100 HTTP seats с save/read** и проверкой
  cleanup. Это **не 100 одновременно открытых браузерных редакторов**, не
  проверка WebGL/GPU всех клиентов и не доказательство полной ёмкости сервера.
  Область HTTP-проверки описана в [документе38](38-SCHOOL-HTTP-LOAD-100.md).

## Возврат: сначала данные, затем маршрут

| Момент отказа | Действия |
| --- | --- |
| До любых школьных записей после финального среза | Закрыть школьную запись, подтвердить отсутствие её новых данных и сохранность H04 на финальном состоянии. Вернуть зафиксированные маршруты/конфигурацию и открыть H04 единственным writer; повторить HTTPS/login/read/save проверки. Это допустимо только при доказанном отсутствии новых школьных записей. |
| После любых школьных записей, включая QA/сессии/фоновые задания | Закрыть запись на обоих узлах, сохранить согласованную школьную БД, объекты и журналы. Перенести последнее школьное состояние в подготовленную совместимую цель на H04 либо выполнить проверенное reconciliation новых данных, явно учитывая собственные QA-записи. Сверить данные/объекты, ключи, права и работоспособность. Только затем вернуть маршрут и открыть H04 единственным writer. Дамп schema307 нельзя молча вернуть в старый runtime/schema H04. |

**Простое DNS-назад к прежней H04-БД после школьных записей недопустимо:**
оно оставляет эти записи в другой базе. Если последнее состояние пока нельзя
получить или согласовать, сохраняется режим без записи и выполняется восстановление
данных; старую копию нельзя выдавать за полный возврат без потерь.

Нынешние old OID26362/fenced и last-write копия **2325 файлов / 187358281 байт**
относятся **только к выполненному staging refresh школьного X**. Основа будущего
production-возврата — заново зафиксированные при финальной остановке записи
**H04: его БД, объекты и проверенный архив**. Старый школьный baseline этой точкой
не является; после новых школьных записей добавляется обратный перенос/согласование.

Изолированные PostgreSQL/object proofs и восстановление конкретных архивов
подтверждают свои области подготовки. **Полный live rollback NOT_RUN.** Они
не доказывают возврат после будущих production-записей. Новая копия после
refresh уже создана и [принята по облачному ciphertext](../snapshots/2026-11-08/school-post-refresh-backup-0252-root-acceptance-20261108.json),
но её decrypt/внутренний manifest/PG+MinIO restore ещё не подтверждены;
проверки прежних архивов её не заменяют.

## Backup и журналы во время окна

Школьный таймер — **03:20 Europe/Moscow**. Не накладывать ручной перенос на
активный backup. Native backup временно останавливает writers и возобновляет
сервисы в finally; после него проверить сохранность требуемого запрета записи,
health и фактический lifecycle. Возможный новый StartedAt `migration`/`minio-init`
разбирается по наблюдению; будущие значения не подставляются, strict guard
не ослабляется заранее.

В [срезе03](../snapshots/2026-11-08/actual-logging-observation-20261108T000720Z.json)
приняты свежие данные всех26 обязательных collector sources; история имеет
`coverageComplete=false` и lifecycle gap. [03A](../snapshots/2026-11-08/actual-apply-20261108T002312Z.json)
подключил школьный backup receipt. **Authenticated API requiredCoverage пока
не принят**; свежесть sources не закрывает исторический пробел. Перед/после окна
сохранить и проверить отдельно collector/native/host-журналы: полная история
логов находится вне portable PostgreSQL+MinIO backup, восстанавливать её из
такого архива по умолчанию нельзя.
